Agent Wiring Map

How an agent tool reaches your use cases without breaking Clean Architecture: what happens on a request, how main.go wires it, and which files to touch when you add a tool or an agent.

interfaces/ (handlers, tools) applications/usecases infrastructures/ outside the service
1 · on every request

A chat request, step by step

The agent never touches your database. When the model wants data, the agent calls a tool, and the tool calls a use case exactly like an HTTP handler would. Steps 4 to 10 repeat until the model stops asking for tools.

2 · once, at startup

How main.go wires it

Each piece is built once and passed into the next, the same way you already pass repositories into use cases and use cases into handlers. The agent only receives the tools as values, so infrastructures/ never imports interfaces/.

// main.go (example names: orders + chat do not exist yet; system does)
mainLLM := langchain.NewLangChainInstance(configs, configs.Envs.MainLLM)

ordersRepositories := repositories.NewOrdersRepositories(dbInstances)
ordersUsecase := usecases.NewOrdersUsecase(ordersRepositories)

agentTools := agent_tools.NewAgentTools(systemUsecase, ordersUsecase)

supportAgent := &agents.Agent{
	Name:         "support",
	LLM:          mainLLM,
	SystemPrompt: supportPrompt, // utils.GetAgentPromptFileContent("support.md")
	Tools:        agentTools.Orders.RegisterTools(),
}

chatUsecase := usecases.NewChatUsecase(supportAgent)
chatHandler := chat.NewChatHandler(chatUsecase)
chatHandler.RegisterRoutes(e.Group("/chat"))
3 · several agents, several models

Multi-agent with different models

A sub-agent is just another tool. researcher.AsTool(…) gives the coordinator a tool named researcher that takes a task and returns the researcher's answer. Each agent picks its own model.

fastLLM := langchain.NewLangChainInstance(configs, configs.Envs.FastLLM) // FAST_LLM_PROVIDER, FAST_LLM_MODEL…

researcher := &agents.Agent{Name: "researcher", LLM: fastLLM, SystemPrompt: researcherPrompt,
	Tools: agentTools.Search.RegisterTools()}
writer := &agents.Agent{Name: "writer", LLM: mainLLM, Model: "claude-sonnet-5-5", SystemPrompt: writerPrompt}

coordinator := &agents.Agent{
	Name:         "coordinator",
	LLM:          mainLLM,
	SystemPrompt: coordinatorPrompt,
	Tools: append(agentTools.Orders.RegisterTools(),
		researcher.AsTool("Finds facts. Give it one precise question."),
		writer.AsTool("Writes the final reply from the facts you give it."),
	),
}
recipe

Adding a new tool: four files

Example: let agents look up an order. The use case and repository are the ones your HTTP endpoints already use; the tool only adds a new way in.

  1. Describe the input commons

    commons/models/orders.go

    Same tags as an HTTP request model, plus description. The JSON schema the model sees is generated from this struct, and the arguments are validated with it.

    type GetOrderToolInput struct {
	OrderID string `json:"order_id" validate:"required" description:"The order ID, e.g. ord_123"`
}

  2. Write the tool like a handler interfaces

    interfaces/agents/orders/handler.go

    The struct holds the use cases. Each tool method gets ctx and the decoded input, calls the use case, and returns JSON. No business logic here.

    package orders_agent

type OrdersAgentTools struct {
	ordersUsecase *usecases.OrdersUsecase
}

func NewOrdersAgentTools(ordersUsecase *usecases.OrdersUsecase) *OrdersAgentTools {
	return &OrdersAgentTools{ordersUsecase}
}

// Mirrors RegisterRoutes in interfaces/http
func (h *OrdersAgentTools) RegisterTools() []agents.Tool {
	return []agents.Tool{
		agents.NewTool("get_order",
			"Returns an order's status and items. Use it when the user asks about an order.",
			h.GetOrder),
	}
}

func (h *OrdersAgentTools) GetOrder(ctx context.Context, input models.GetOrderToolInput) (string, error) {
	order, err := h.ordersUsecase.GetOrder(ctx, input.OrderID)
	if err != nil {
		return "", err // see "What the model sees" below
	}
	return agents.JSON(order)
}

  3. Register the domain interfaces

    interfaces/agents/handler.go

    Add a field and the use case parameter, like adding a handler to the router.

    type AgentTools struct {
	System *system_agent.SystemAgentTools
	Orders *orders_agent.OrdersAgentTools // new
}

func NewAgentTools(systemUsecase *usecases.SystemUsecase, ordersUsecase *usecases.OrdersUsecase) *AgentTools {
	return &AgentTools{
		System: system_agent.NewSystemAgentTools(systemUsecase),
		Orders: orders_agent.NewOrdersAgentTools(ordersUsecase), // new
	}
}
// and add t.Orders.RegisterTools() to All()

  4. Give it to an agent main.go

    main.go

    Pass the use case in, then list the tools on the agents that should have them.

    agentTools := agent_tools.NewAgentTools(systemUsecase, ordersUsecase)
supportAgent.Tools = append(supportAgent.Tools, agentTools.Orders.RegisterTools()...)
errors

What the model sees when a tool fails

The same rules as utils.ErrorResponse. The model reads the result as text and may repeat it to the user, so internal details must never get there.

Your tool returnsThe model seesWhy
utils.NewNotFoundError(…), NewClientError, … Error: order ord_123 not found A message meant for the caller, so the model can react (ask for another ID, explain).
Input that fails validate or isn't valid JSON Error: invalid arguments for get_order: … The model made a mistake and can retry with fixed arguments.
Any other error (SQL, network) or a panic Error: the tool failed with an internal error (error id …) The real error is logged with that ID and the request ID, like a 500 response.
the other end

Running the agent from a use case

A use case calls Run; the HTTP handler streams the tokens as SSE. Add the route to models.RequestTimeoutSkipPaths, or REQUEST_TIMEOUT cuts long answers off.

// applications/usecases/chat.go
type ChatUsecase struct {
	supportAgent *agents.Agent
}

func (u *ChatUsecase) Chat(ctx context.Context, message string, history []llms.MessageContent,
	onToken func(ctx context.Context, chunk string) error) (*agents.Result, error) {
	return u.supportAgent.Run(ctx, message, agents.WithHistory(history), agents.WithOnToken(onToken))
}

// interfaces/http/api/chat/handler.go
func (h *ChatHandler) PostChat(c echo.Context) error {
	ctx := c.Request().Context()
	// bind + validate models.ChatRequest as usual …
	_, err := h.chatUsecase.Chat(ctx, req.Message, history, func(ctx context.Context, chunk string) error {
		return utils.SuccessResponseSSEvent(c, utils.SuccessResponseSSEventConfig{
			Event: "token", Data: map[string]string{"token": chunk},
		})
	})
	if err != nil {
		return utils.ErrorResponseSSEvent(c, err)
	}
	return utils.SuccessResponseSSEvent(c, utils.SuccessResponseSSEventConfig{Event: "complete", Data: "[DONE]"})
}

Save Result.Messages after each run and pass it back with agents.WithHistory to continue the conversation. With Claude, keep one conversation's tool loop on one instance: the adapter keeps Claude's reasoning between tool calls in memory.
